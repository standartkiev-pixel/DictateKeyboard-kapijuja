# Kapijuja Driver Assistant — техническое задание для Dictate Kapijuja Keyboard

**Статус:** proposal / спецификация, реализация не начата  
**Дата:** 2026-11-11  
**Репозиторий:** `standartkiev-pixel/DictateKeyboard-kapijuja`  
**Связанный проект для технических решений по TTS:** `standartkiev-pixel/kapijuja-reader`  
**Назначение:** доступное, быстрое и управляемое голосовое чтение скопированных сообщений и помощь в ответах через WhatsApp/Viber и другие мессенджеры с минимальным взаимодействием с экраном. **Никакой автоматической отправки сообщений.**

## 0. Принцип проектирования

Расширять **существующую клавиатуру**, не создавать отдельное приложение. Не ломать рабочие функции записи, распознавания, истории, буфера обмена, Smartbar, плавающей кнопки, восстановление аудиозаписей и текущие настройки. Новые функции независимы, изначально выключены и явно включаются пользователем.

Цель — «клавиатура для водителя»: быстро услышать скопированное сообщение, при необходимости открыть переписку, нажать существующий микрофон, продиктовать ответ и **самостоятельно** нажать отправку. Сценарий проектируется для минимизации взаимодействий и отвлечения; использование интерфейса во время движения не должно требовать чтения экрана или точных нажатий.

## 1. Готовая основа в исходном коде

- `app/src/main/kotlin/dev/patrickgold/florisboard/ime/clipboard/ClipboardInputLayout.kt`: история, элементы, поиск, закрепление, удаление, popup; нужен значок динамика на элементах типа TEXT.
- `app/src/main/kotlin/dev/patrickgold/florisboard/app/AppPrefs.kt`: clipboard settings; внутренний буфер и история включены по умолчанию, стандартный лимит истории — 90 записей.
- `app/src/main/kotlin/dev/patrickgold/florisboard/dictate/overlay/DictateAccessibilityService.kt`: существующая **опциональная** служба Accessibility для плавающей кнопки ввода и определения поля, куда вводить текст; **сейчас она не служит универсальным экранным чтецом**.

Следовать `DEVELOPER_HANDOFF.md`, `DEVELOPER_GUIDE.md` и текущей архитектуре клавиатуры; сперва читать только относящиеся к задаче файлы.

## 2. Сценарий А: автоматическое чтение нового содержимого буфера обмена

### 2.1. Быстрый переключатель

- Добавить **кнопку динамика в самом левом доступном месте панели клавиатуры / Smartbar**; справа остаётся существующий микрофон. Значки чтения и записи должны быть визуально и семантически различимы. Не делать тусклую маленькую неразличимую кнопку.
- Короткое нажатие: включить/выключить **автозачитывание новых текстовых элементов буфера**. Состояние видно постоянно при показанной клавиатуре; сохраняется между перезапусками до ручного изменения. **По умолчанию OFF.**
- Долгое нажатие (или понятное меню): настройки озвучивания. Обеспечить TalkBack labels.
- Не путать «автозачитывание» с голосовой **диктовкой**: кнопка отключает только чтение, не микрофон/STT.
- Если места недостаточно — аккуратно уменьшить/перекомпоновать декоративную осциллограмму, **не удаляя индикатор активной записи, уровень/состояние микрофона и сигналы ошибок**. Зафиксировать скриншотами портрет/ландшафт/крупный шрифт.

### 2.2. Триггер

- При новом системном текстовом ClipData, когда автозачитывание включено и система реально разрешает доступ текущей IME, создать **одну** сессию ожидания чтения. ИСПОЛЬЗОВАТЬ существующий `ClipboardManager`, не создавать второй независимый listener/историю.
- Не запускать по: пустому содержимому, картинкам/видео/URI без текста, дублирующему изменению одного и того же клипа, собственным служебным копированиям клавиатуры, помеченному чувствительному ClipData, паролю, OTP/2FA и явно определённым секретам. Фильтры best-effort, не обещать надёжного распознавания всех секретов; окончательная защита — opt-in, отмена, режим безопасности, отсутствие облака по умолчанию.
- Не преобразовывать произвольно URI/HTML в сетевые запросы и не читать системные секреты. Учитывать требования и ограничения clipboard на Android 10+.
- Поскольку выбранная системная клавиатура имеет особый доступ к Clipboard, тестировать **реальное** срабатывание с закрытой клавиатурой, в фоне, при выключенном экране, после выгрузки процесса и в Samsung One UI. Не гарантировать непрерывный monitoring, пока не измерено.

### 2.3. Обязательное окно предупреждения и отмены

- **Сразу после обнаружения клипа, до начала озвучивания** показать компактное ненавязчивое окно/overlay, если разрешены видимость окна/состояние экрана.
- **Задержка по умолчанию 3 секунды.** В настройках — 2 / 3 / 5 / 10 секунд (возможен расширенный диапазон после тестов). Обратный отсчёт в интерфейсе **строго равен настроенной задержке**; при 2 сек нельзя писать «через 3».
- Пример: «Новый текст. Автоматическое чтение через 3… 2… 1…».
- Две большие однозначные кнопки в **этом же окне**:
  1. **«Отмена»** — отменяет **только текущую** сессию, не меняя включённый режим.
  2. **«Выключить автозачитывание»** — отменяет текущую сессию, немедленно останавливает ожидающее/текущее чтение и **отключает автозачитывание в настройках до ручного нового включения**. Не надо открывать настройки.
- Дополнительно можно дать «Читать сейчас», если хватает места, но **не вместо** двух обязательных кнопок.
- Окно и кнопки должны быть доступны при открытом WhatsApp/Viber и не закрывать текст ответа/кнопку отправки без необходимости.
- Если overlay недоступен, устройство заблокировано, на экране показывать нельзя или безопасность условий сомнительна — **не стартовать молча автоматическое чтение**; вместо этого дать доступный системный action notification / отложить до явного действия пользователя. Не выводить текст на заблокированный экран.
- При каждой новой копии пока идёт countdown отменить предыдущий countdown и заменить новым (**latest wins**). Если чтение уже идёт, остановить/заменить по задаваемой политике (по умолчанию latest wins). Удалённые сессии ни при каких условиях не должны начать воспроизведение позже.
- При повторном копировании ранее прочитанного текста как новом явном действии пользователя разрешить новое чтение; подавлять именно двойные системные callbacks, а не любые совпадающие строки навечно.
- Состояние OFF/ON и отмена применяются синхронно. Проверять токен поколения непосредственно перед TTS, перед запросом в облако и после асинхронного ответа; исправить гонки stop/cancel/next.

### 2.4. Чтение элемента истории

- Рядом с каждым элементом TEXT на `ClipboardInputLayout` добавить небольшую, но легко доступную **кнопку динамика**.
- Нажатие динамика: чтение выбранного текста **сразу по явному действию**, без задержки и без вставки текста в поле; отдельное нажатие на сам текст сохраняет стандартную вставку. Поддержать повтор/пауза/стоп.
- Не дублировать БД и не переносить историю в Reader. Уважать pinned, удаление, expiry и защиту чувствительных записей.

## 3. Три TTS-движка — выбираются в настройках

1. **Android TextToSpeech (default):** установленный системный движок и голоса, язык/скорость/темп. Быстро, без необходимости сетевой передачи текста самой клавиатурой; конкретный голос может быть сетевым — определить через свойства Android voice.
2. **OpenAI speech:** облачный голос OpenAI через **официальный API с ключом пользователя** (не «голос подписки в приложении ChatGPT»). Использовать UX и архитектурные решения Kapijuja Reader как ориентир; поддерживаемые актуальные модели/голоса, тест соединения, стоимость и ограничение расходов. **Не захардкодить устаревающие `tts-1`, `tts-1-hd`, `gpt-4o-mini-tts`: на дату задания официальная документация OpenAI объявляет отключение этих Speech API моделей 2027-01-06; проверить поддерживаемый новый интерфейс, в т. ч. Realtime API, до реализации.**
3. **Microsoft Azure Speech:** ключ пользователя + регион, голос, язык, тест соединения; ориентир `AzureTtsClient` в Reader.

Общий интерфейс `SpeechEngine` / `TtsCoordinator`: `speak(text, sessionId)`, `stop()`, `pause/resume` где поддерживается; engine adapters изолированы. Ошибка платного движка: предложить/применить настраиваемый fallback к Android TTS, без повторных оплачиваемых запросов. По умолчанию не отправлять скопированные сообщения в облако; при выборе Azure/OpenAI показать явное согласие и уведомление, что текст уходит провайдеру и возможны расходы. Ключи не логировать, хранить в защищённой конфигурации приложения. Не делать eager TTS запрос до окончания countdown (это также предотвращает оплату отменённого чтения). Стараться не синтезировать длинный текст целиком вперед; ограничения на длину/очередь/таймаут и стоимость.

**Лицензии:** Reader распространяется под GPL-3.0-or-later, Keyboard — Apache-2.0. Прямое копирование GPL-кода Reader в Apache-only приложение без корректного изменения лицензионной модели недопустимо. Возможны независимая реализация адаптеров по публичной документации/SDK, корректная юридически лицензированная переиспользуемая библиотека либо взаимодействие двух установленных приложений через публичный Intent/API с отдельным согласием; **предпочтение — независимая минимальная реализация в Keyboard**. Не копировать `OpenAiTtsClient.kt` или `AzureTtsClient.kt` вслепую.

## 4. Сценарий Б: получено новое сообщение WhatsApp/Viber → подготовить ответ

### 4.1. Отдельная настройка

- `Driver Assistant → Автоматически подготовить ответ на новое сообщение`, по умолчанию **OFF**; отдельные переключатели WhatsApp и Viber (возможна расширяемая allowlist других приложений).
- После добровольного системного разрешения **Notification Access** слушать входящие уведомления через `NotificationListenerService`. Не читать их через Accessibility polling всего экрана.
- Реагировать только на реальные новые сообщения в выбранных приложениях. Дедуплицировать обновление notification, grouped notifications, summary, сообщения пользователя самому себе, тихие служебные события и повторную доставку.
- Не отправлять ответ, не нажимать кнопку Send, не начинать запись микрофона без явного действия.

### 4.2. Открытие соответствующего чата

- **Желаемый UX:** при поступлении уведомления приложение открывает именно чат отправителя (WhatsApp/Viber), когда пользователь включил автоматизацию, и в нужном чате становится доступна наша клавиатура с курсором в поле ответа.
- **Технически обязательная реализация с fallback:** использовать notification's `contentIntent`/официальные documented deep links, если они реально открывают нужный чат. Из Android 10+ существуют Background Activity Launch restrictions; Android 14/15+ ужесточают `PendingIntent`, нельзя обещать безусловное самооткрытие чужой Activity с фона. При технической/системной невозможности автоматически всплывает **одно действие** «Открыть чат и ответить» в своём уведомлении или видимой кнопке/оверлее; по нажатию пользователя открыть *точный* чат через notification contentIntent. Не подменять этот сценарий открытием случайного последнего чата.
- В настройках экспериментальная опция «Пытаться автоматически открывать чат, когда это разрешено системой» с явным предупреждением: на разных версиях Android/состояниях экрана сработает не всегда; обязательно сохранён надёжный ручной путь одной кнопкой.
- После фактического открытия и только когда Accessibility включена, проверить **реально видимый** корректный editable узел в WhatsApp/Viber и безопасно запросить фокус на поле ответа, открыть клавиатуру. Не делать неограниченные сканирования/клики по координатам, не вводить в неизвестное поле, не перехватывать данные иных приложений. Если фокус не подтверждён, оставить пользователю понятную кнопку «Нажмите поле ответа», а не делать вид, что всё готово.
- Если уведомление скрывает содержимое или `contentIntent` не даёт конкретного чата — показать краткое «Открыть мессенджер», не угадывать отправителя.
- **Экран заблокирован, активный звонок, DND, опасное состояние, запрещённые системные overlay/permissions:** не делать агрессивное автоматическое переключение экрана; fallback через уведомление/отложенное действие пользователя.
- В будущих версиях опционально можно добавить отдельную настройку чтения *текста уведомления* с такой же защитой и countdown; **не смешивать этот поток** с чтением буфера, пока пользователь не включил его отдельно.

### 4.3. Ответ

- Существующая кнопка микрофона и STT работают без изменения. Пользователь явно запускает запись и подтверждает/корректирует текст штатными возможностями клавиатуры.
- Отправка — **только по нажатию пользователем** в самом мессенджере. Без автоматической отправки или автонажатия клавиши Enter/Send.
- Поля отправителя/чата могут быть приватными; в логах не хранить текст сообщений.

## 5. UX, расположение, настройки

Настройки сгруппировать в самостоятельный небольшой экран **«Driver Assistant / Чтение и ответы»**:
- Автозачитывание нового текста буфера: OFF по умолчанию; быстрый переключатель **слева** в Smartbar.
- Задержка: **3 с по умолчанию**, варианты 2/3/5/10 с.
- Движок TTS: Android (по умолчанию), OpenAI, Azure; голос, скорость, пример звучания; параметры ключа/региона только для выбранного облака.
- Звуковой выход: уважать системную маршрутизацию Bluetooth/динамик, Android AudioFocus и прерывание от навигации/телефонных звонков; не включать громкую связь самовольно.
- Политика новых клипов: latest wins / очередность (первый выпуск: latest wins); поведение после отмены: выключить один раз или полностью через разные кнопки.
- Подготовка ответа на уведомление: OFF, WhatsApp, Viber, experimental auto-open и разрешения.
- Наглядный status: чтение включено/выключено; говорящий/ожидающий/отменённый/ошибка.
- Режим работы без экрана, сохранение состояния при смене ориентации, корректные размеры кнопок, уважение к системному крупному шрифту и TalkBack. Не размещать переключатель озвучивания рядом с микрофоном.

## 6. Архитектура — без распухания существующих монолитных файлов

Предлагаемые отдельные небольшие компоненты (имена предварительны):
- `driver/DriverAssistantPreferences.kt` — настройки / миграция.
- `driver/ClipboardSpeechObserver.kt` — подписка на существующий clipboard flow и фильтр новых клипов.
- `driver/ClipboardReadStateMachine.kt` — Idle / Countdown / Speaking / Cancelled / Disabled и одноразовый generation token.
- `driver/ClipboardReadPromptController.kt` — счётчик, отмена, disable, доступный overlay/notification fallback.
- `driver/speech/TtsCoordinator.kt`, `AndroidSpeechEngine.kt`, `OpenAiSpeechEngine.kt`, `AzureSpeechEngine.kt`.
- `driver/DriverNotificationListenerService.kt` — только разрешённые уведомления; lifecycle, дедупликация, фильтр отправителя.
- `driver/ConversationOpenCoordinator.kt` — contentIntent, Android BAL permission-aware fallback, проверка целевого чата; интеграция с уже существующей Accessibility службой без её превращения в универсальный screen scraper.
- `driver/ui/DriverAssistantSettingsScreen.kt` и небольшие интеграции в ClipboardInputLayout / Smartbar.

**Модель состояний:** OFF → ON_IDLE → COUNTDOWN(sessionId, clipId, deadline) → SPEAKING(sessionId) → ON_IDLE; Cancel → ON_IDLE; Disable → OFF с немедленной отменой всех будущих запусков и текущего playback. Новый клип инкрементирует session generation; callback от старой сессии ничего не запускает. Новая запись микрофона имеет приоритет: чтение ставится на паузу/останавливается, чтобы TTS не попадал в STT. Не допускать TTS и записи одновременно по умолчанию.

## 7. Защита данных и контроль затрат

- Opt-in на каждый автоматический режим: clipboard read и notification assistant — отдельно. Никаких фоново включённых отправок текста.
- Никогда не произносить клип, помеченный `ClipDescription.EXTRA_IS_SENSITIVE`; пароли/OTP/банковские данные блокировать best effort, без претензии на безошибочную классификацию. Возможны ручные исключения приложений, если источник надёжно известен; если нет — не утверждать атрибуцию.
- Никакой публикации содержимого уведомлений/буфера в Crashlytics, логи, аналитические события или исходный код. Не создавать вторую историю.
- По умолчанию локальный Android TTS; OpenAI/Azure только после выбора, предоставления ключа и согласия на передачу содержимого. Возможность мгновенно отменить **до начала платного запроса**.
- Не показывать содержимое сообщений на заблокированном экране. Принудительный stop TTS при disable, отзыве разрешений, смене профиля, чувствительном состоянии, завершении процесса.
- Редактируемый ответ никогда не отправляется программно.

## 8. Проверки и критерии готовности (acceptance criteria)

1. После включения автозачитывания копия обычного текста из WhatsApp/Viber создаёт **один** countdown; по умолчанию видны 3→2→1, после него — чтение. При задержке 2 с на экране точно 2→1.
2. **«Отмена»** предотвращает TTS/облачный запрос именно этого клипа, следующий клип снова вызывает countdown.
3. **«Выключить автозачитывание»** отменяет текущую сессию, останавливает речь и сохраняет OFF; очередные копирования **не** запускают озвучку до включения левой кнопкой.
4. Левая кнопка не пересекается с правым микрофоном, статус понятен; STT, запись, восстановление, History, Smartbar работают как до изменений. В частности, нельзя удалить сохранённую аудиозапись одним случайным нажатием.
5. Отдельный динамик на **каждом** текстовом элементе истории читает его без вставки; стандартное нажатие по карточке по-прежнему вставляет.
6. Отмена/новый клип/потеря сети/завершение асинхронного старого TTS не вызывают чтение отменённой сессии и не порождают дублирующий оплачиваемый запрос.
7. Системный Android TTS работает с выбранным голосом; OpenAI/Azure имеют тесты подключения, ошибки и fallback; ни текст, ни ключи не попадают в логи.
8. При входящем notification WhatsApp/Viber и отдельном opt-in создаётся точный переход к чату **когда это разрешено платформой**; в иных случаях есть **одно нажатие** для открытия нужного чата; нет принудительного бесконечного открытия мессенджера.
9. При реальном переходе в чат и подтверждённом поле ответа клавиатура готова принять микрофонный ввод; **никогда** не отправляет сообщение без человека.
10. Не читать секреты, помеченные sensitive; не озвучивать при блокировке экрана без разрешённой явной политики. Правильно обрабатывать пустой/нетекстовый клип, дубликаты, массовое копирование, быстрые cancel/enable, звонки, навигацию, Bluetooth.
11. Проверить Android 10–17 по доступным устройствам/эмуляторам, в первую очередь Samsung Galaxy One UI (включая Android 17): клавиатура видима/скрыта, фон, процесс убит, notification access отсутствует/отозван, overlay отсутствует, lock screen, режим энергосбережения.
12. Сборка debug APK + unit tests в GitHub Actions; логика race/cancel/countdown/дедупликации покрыта автоматическими тестами. Для Android platform behavior — instrumented/manual verification с явными результатами, а не предположение о доступности API.
13. После реализации обновить `DEVELOPER_HANDOFF.md`, `DEVELOPER_GUIDE.md`, README, документацию настроек; описать реальные ограничения Android и лицензий.

## 9. Этапы внедрения (не выполнять всё одним большим PR)

- **P0** — отдельная подсистема локального Android TTS + ручная кнопка динамика на истории + тесты: минимально рискованный функциональный выпуск.
- **P1** — быстрый левый переключатель + clipboard observer + предупреждение/countdown 2/3/5/10 + Cancel/Disable + отмена гонок + security safeguards.
- **P2** — OpenAI и Azure (модульные адаптеры с проверкой актуального API, безопасностью ключей и стоимости).
- **P3** — NotificationListenerService WhatsApp/Viber + отдельный opt-in + точный переход к чату через notification contentIntent и однокнопочный fallback.
- **P4** — экспериментальный авто-переход и безопасная постановка курсора с подтверждением editable через существующую Accessibility службу; тесты на реальных сборках WhatsApp/Viber и Android/One UI.
